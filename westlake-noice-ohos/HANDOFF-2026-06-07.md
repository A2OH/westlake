## Goal details + root causes

### 1. SCROLL (deployed: bridge d2e50209)
- **Root cause:** real-finger touch only worked for UP. `OHInputBridge::dispatchTouchViaViewRoot`
  had `if (action != 1 /*UP*/) return 0;` and synthesized a *stationary* tap — so the real DOWN
  and all MOVE samples were discarded → RecyclerView/ScrollView never saw a moving pointer → no scroll.
  (Only the control-channel `dispatchDragViaViewRoot` scrolled, because it builds a real DOWN→MOVE→UP.)
- **Fix:** added `OHInputBridge::dispatchSingleTouchViaViewRoot(action,x,y,downNs,evtNs)` that forwards
  the REAL action via `OHTouchInjector.dispatchTouchOnMain` (MotionEvent.obtain(downMs,evtMs,action,x,y,0)),
  and routed the real-MMI path (`OnInputEvent(PointerEvent)`, ~line 1211) to it.
  Tab-proxy (~line 1202) + control-channel (~1272) still use `dispatchTouchViaViewRoot` (unchanged).
- **Files:** `$HOME/bridge-build/src/framework/window/jni/oh_input_bridge.{h,cpp}`
- **Build:** `cd $HOME/bridge-build && OH_ROOT=$HOME/openharmony AOSP_ROOT=$HOME/bridge-build/aosp ADAPTER_ROOT=$HOME/bridge-build BRIDGE_TMP=/tmp/bridge_build bash build/build_adapter.sh --target=liboh_adapter_bridge.so` → `out/adapter/liboh_adapter_bridge.so`
- **Deploy:** push to **`/system/lib/liboh_adapter_bridge.so`** (NOT /system/android/lib — noice loads /system/lib/), chmod 644 + chcon system_lib_file, reboot.
- **VALIDATE:** real-finger slow-drag on a noice list → it scrolls. Check child stderr for `dispatchSingleTouch` action=0 then action=2 (several) then action=1, no `THREW`.
- **TODO (fling):** quick flick still won't fling — VelocityTracker natives return 0. Add a functional velocity ring-buffer in `ensureVelocityTrackerStub` (compute vx/vy from MOVE deltas in nativeComputeCurrentVelocity/nativeGetVelocity). Slow drag works without it.

### 2. SHARE (deployed: ohaf efd3f740 + regenerated boot)
- **Root cause:** NOT stale boot, NOT a different intent. The chooser unwrap (deployed earlier as
  300581d1) IS live. The crash: after unwrap, ACTION_SEND → `ohos.want.action.sendData` has NO OHOS
  handler → `nativeStartAbility` returns a NEGATIVE error → AOSP `Instrumentation.checkStartActivityResult`
  throws `ActivityNotFoundException` (uncaught) → crash. (An earlier "graceful dialog" run was when it returned 0.)
- **Fix:** in `adapter/activity/ActivityManagerAdapter.bridgeStartAbility` (in oh-adapter-framework.jar),
  clamp a negative `nativeStartAbility` result → 0 (START_SUCCESS) with a `Log.w("...clamping to START_SUCCESS...")`.
  Unhandled share now degrades gracefully (OHOS shows its own "无法打开此文件" dialog) instead of crashing.
  Preserves the chooser unwrap (both verified present in the new dex + boot vdex).
- **Files:** smali-patched the deployed jar. Source-of-truth reference: `share-fix/IntentWantConverter.java`
  (chooser unwrap) + the clamp is a smali edit in ActivityManagerAdapter (documented here + in memory).
- **Build:** baksmali deployed ohaf → edit ActivityManagerAdapter.smali (`if-gez p1, :cond_amok` ... `const/4 p1, 0x0`)
  → reassemble via `java -cp $HOME/apktool.jar:/tmp SmaliAssemble <smalidir> classes.dex 30`
  → zip into jar copy. Staged jar: **`/tmp/ohafchk/ohaf_clamp.jar`** (efd3f740).
- **Deploy:** ohaf is in the BCP (last jar) → must regen boot image. Stage jar → `/tmp/tagsoup-boot/jars/oh-adapter-framework.jar`
  → `bash /tmp/tagsoup-boot/regen.sh` → push jar to `/system/android/framework/oh-adapter-framework.jar` + boot image
  (`/tmp/tagsoup-boot/out/boot*`) to `/system/android/framework/arm/`, reboot.
- **VALIDATE:** account tab → 支持开发 → 与朋友分享 → noice pid SURVIVES (no crash), child stderr shows
  `clamping to START_SUCCESS` + 0 `ActivityNotFoundException`/FATAL; OHOS dialog OK.

### 3. STABILITY (deployed: start_asx.sh G5 + launch_noice.sh) — 8/8 proven
- **Root causes:** (a) `start_asx.sh` did `rm -f /dev/unix/socket/AppSpawnX` → AMS binds to that inode,
  removing it detached routing → "aa start succeeds but no fork" wedge. (b) AMS↔appspawn-x RACE: AMS connects
  before appspawn-x reaches "Phase 4: Ready to accept spawn requests" → EPIPE → persistent wedge.
  (c) A TIGHT bpfgrant loop destabilizes the kernel → full-device reboot loop (THIS is what looked like
  "repeating rebooting").
- **Fixes (on device at /data/local/tmp/):**
  - `start_asx.sh` — does NOT rm the socket; ensures /dev/memcg/perf_sensitive; keeps the LD_PRELOAD shims.
  - `launch_noice.sh` — deterministic launcher: waits for "Phase 4" before aa start; does NOT restart
    appspawn-x as recovery (exits LAUNCH_NEEDS_REBOOT instead); **rate-limits bpfgrant (sleep 2)**;
    correct child detection (uid 13731 appspawn-x child). Output: LAUNCH_OK / LAUNCH_NEEDS_REBOOT / LAUNCH_FAIL.
- **Result:** 8/8 GOOD launches across 8 reboots (first-try 7/8). Lottery fixed.
- **IMPORTANT going forward:** ALWAYS run the network grant rate-limited: `while true; do bpfgrant 13731 oh_sock_permission_map; sleep 2; done` (a tight loop bricks into a reboot loop). Use `launch_noice.sh` to launch.

## CONNECTION — reconnect after the Windows reboot (READ FIRST)

The board connects to WSL via hdc (`/mnt/c/Users/dspfa/Dev/ohos-tools/hdc.exe`). After ANY reboot
(device OR Windows), hdc often shows `[Empty]` / `ERROR: UtilAcceptVsock ... accept4 failed 110` — this is
the **WSL↔device transport dropping, NOT a device fault** (this session it was misdiagnosed as a bootloop;
the board was actually fine and running the deployed boot).

To reconnect:
1. `/mnt/c/Windows/System32/taskkill.exe /F /IM hdc.exe` then `hdc.exe start`, then `hdc.exe list targets`.
2. If still `[Empty]`: **re-plug the USB cable** between board and PC (and accept any on-device
   "allow USB debugging" prompt). Then repeat step 1.
3. hdc.exe MANGLES absolute WSL send/recv paths — stage via the Windows dir:
   `cp f /mnt/c/Users/dspfa/Dev/ohos-tools/NAME; hdc.exe file send 'C:\Users\dspfa\Dev\ohos-tools\NAME' /data/local/tmp/NAME` (recv similarly).
4. Device shell sometimes loses `tr`/`awk` after reboot — do text processing HOST-SIDE (pipe `hdc shell "ps -ef"` into host grep/awk).

NOTE: the auto-restore watcher from this session has been STOPPED (it did NOT fire — confirmed it did not
overwrite the deployed scroll+share). Do not expect it running after the Windows reboot.
