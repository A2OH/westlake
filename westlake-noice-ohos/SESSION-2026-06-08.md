## Why a fresh GitHub checkout still can't boot the device

This repo is comprehensive for the **rebuildable + small** half — it commits
libart (`7b856a2d`), all BCP jars, the LD_PRELOAD shims, the native TLS shim,
SSLSockets, the chooser share-fix, a bridge `.so`, docs and `collect-artifacts.sh`.

But four artifacts are **inherently not in git** (un-rebuildable or too large) and
**must be pulled from a live device** with `collect-artifacts.sh`:

| Artifact | device path | why not in git |
|---|---|---|
| `liboh_android_runtime.so` (`f82d8cdc`) | `/system/android/lib/` | **un-rebuildable blob** — no buildable source exists |
| `libhwui.so` (`8b8f84ec`) | `/system/android/lib/` | build env not reproducible on a clean WSL (HBC base) |
| boot image, 30 segments (~143 MB) | `/system/android/framework/arm/boot*` | size; must be the **same dex2oat pair** as the committed libart |
| `framework.jar` (`8524dc56`, ~15 MB) | `/system/android/framework/` | size (rebuildable from `framework-smali-patches/`) |

**That is the real reason the other engineer can't reproduce from a checkout
alone:** without a working device (or a collected tarball of the four above),
there is nothing to boot — and the runtime can't be regenerated from source. The
recipe is here; the un-rebuildable baseline must be collected. (libart ↔ boot
image must come from one snapshot or you get `LinkageError`.)

fix alone it showed the OHOS no-target dialog "无法打开此文件"; the pasteboard layer

→ no mapAction case → bogus Want → StartAbility fail → `ActivityNotFoundException`.

## Bringup flakiness reminder
~50% of boots are "bad": empty sound library (flow race) or a busy main-thread
spin where posted input never runs (`dispatchTouchViaViewRoot invokeCount>0
runCount=0`, main-thread CPU climbing). A good boot = populated library (~68 KB
screenshot) + near-idle main thread. Reroll (reboot + relaunch) until good.
